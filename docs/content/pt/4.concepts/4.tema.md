Nenhum `ui` do módulo usa token semântico do Tailwind. Toda cor e todo radius
passam por uma variável própria, em forma de *arbitrary property*:

```ts
container: "rounded-(--rf-radius-xl) bg-(--rf-color-background-100) has-[:focus]:outline-(--rf-color-primary)";
```

**Trocar tema é trocar variável — `ui` não se mexe.**

## As 16 variáveis

| grupo | variáveis |
|---|---|
| fundo | `--rf-color-background`, `-100`, `-200`, `-300` |
| texto | `--rf-color-contrast` |
| ação | `--rf-color-primary`, `--rf-color-primary-fg` |
| estado | `--rf-color-danger`, `--rf-color-danger-fg`, `--rf-color-success`, `--rf-color-warn` |
| raio | `--rf-radius-sm`, `-md`, `-lg`, `-xl`, `-2xl` |

## Elas encadeiam no tema do seu app

O default de cada uma é um `var()` com fallback:

```css
--rf-color-primary: var(--color-primary, #005bdf);
```

Então um app que já tem `primary` no `@theme` **adota sozinho** — não há linha
de override a escrever. Foi assim que este site não precisou de nenhuma.

Os degraus `-100`/`-200`/`-300` (10%, 15%, 20%) são derivados com `color-mix`
em vez de encadeados: um `--color-background-100` de outro app pode significar
"tom mais claro" em vez de "10% na direção do contraste".

## Como sobrescrever

Cinco formas, e a ordem dos dois `@import` só afeta duas delas:

| forma do override no app | `#rform` antes | `#rform` depois |
|---|---|---|
| `@theme { --rf-color-primary }` | pega | **ignora** |
| `@layer base { :root { --rf-color-primary } }` | pega | **ignora** |
| `@layer rform { :root { --rf-color-primary } }` | pega | pega |
| `:root { --rf-color-primary }` (fora de layer) | pega | pega |
| `@theme { --color-primary }` (encadeia) | pega | pega |

As três de baixo são imunes à ordem, cada uma por um motivo diferente: mesma
layer resolve por ordem de declaração (e o app vem depois); declaração fora de
layer ganha de toda layer de autor; e `--color-primary` o módulo **nunca**
declara, então não há conflito a resolver — é só o `var(--color-primary, …)` do
default encontrando um valor.

::callout{type="tip"}
As duas formas naturais — encadear pelo `@theme` do seu app, ou declarar
`--rf-*` dentro de `@layer rform` — funcionam nas **duas** ordens. Quem quebra é
declarar `--rf-*` **fora** da `@layer rform` com o `#rform` importado depois — e
aí quebra calado.
::

### Exemplo, encadeando

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@theme {
    --color-primary: oklch(0.6 0.2 250);
}
```

### Exemplo, direto

```css
@import "tailwindcss";
@import "#rform/tailwindcss";

@layer rform {
    :root {
        --rf-color-primary: oklch(0.6 0.2 250);
        --rf-radius-xl: 0.25rem;
    }
}
```

## O que fica literal, de propósito

- `*-current/*` — já é `currentColor`.
- `bg-transparent`, `outline-transparent`.
- `rounded-{full,none,l-none,r-none}` — estruturais, não de tema.
- O `bg-[linear-gradient(…#f00…)]` do matiz no `RColor`.
- O `border-white` dos marcadores do color picker — branco **por desenho**, para
  contrastar com uma cor arbitrária.

Note a assimetria: `text-white` seria drift (virou `-fg`), `border-white` não é.

## A guarda

`test/unit/theme.test.ts` cobre cinco casos, e existe por causa de um modo de
falha que só um teste enxerga: `bg-(--rf-color-primry)` — com o typo — compila,
passa na lint e renderiza `var(--undefined)`, ou seja transparente, **calado em
todo ambiente**.

Os cinco: (a) nenhum token semântico cru voltou; (b) o conjunto de `--rf-*` usado
nos componentes é **igual** ao declarado, nos dois sentidos; (c) o template tem
exatamente um `@source` absoluto apontando para um diretório que de fato contém
os componentes; (d) todo token mora dentro de `@layer rform`; (e) o `style.css`
não tem at-rule do Tailwind.
